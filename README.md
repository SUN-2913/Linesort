# LINESORT — сортировка, дедупликация и очистка больших текстовых файлов

Утилита командной строки на Rust для построчной обработки текстовых файлов
(TXT, CSV, TSV, LOG — любых построчных форматов):

1. **Удаление дубликатов** строк — включая файлы, которые не помещаются в
   оперативную память (внешняя сортировка со слиянием).
2. **Сортировка**: по алфавиту (по умолчанию), естественная (числа как
   числа: `файл2` < `файл10`), без учёта регистра; по возрастанию или
   убыванию.
3. **Обрезка слишком длинных строк** до N **символов** (не байтов —
   кириллица считается по буквам).
4. **Разбивка выходного файла на части** — по числу строк и/или по объёму
   байт; строки никогда не разрезаются посередине.
5. **Обработка каталога**: каждый файл отдельно, либо `--merge` — все
   файлы каталога объединяются в один выход.
6. **Информативный прогресс**: фазы, прогресс-бар со скоростью и ETA,
   итоговый отчёт по каждому файлу и сводка.

Главное свойство: **потребление памяти ограничено бюджетом `--memory` и
НЕ зависит от размера входного файла**. Проверено на файле 1.57 ГБ
(125.7 млн строк): сортировка + дедуп за 86 секунд с пиковым RSS 355 МБ
(бюджет 128M), результат байт-в-байт идентичен GNU `sort -u`.

## Сборка

Требуется Rust 1.75+ (проверено на 1.100). Только стандартная библиотека,
внешних зависимостей нет.

```bash
# Вариант 1: cargo (рекомендуется)
cargo build --release
# бинарник: target/release/linesort

# Вариант 2: одним файлом без cargo
rustc -O linesort.rs -o linesort
```

Юнит-тесты: `cargo test` (20 тестов: компараторы, кодировки, читатель,
арена + потолок серии, сквозная внешняя сортировка, порядок `--no-sort`).

### Windows

Сборка ничем не отличается: установите [Rust](https://rustup.rs), затем

```bat
cargo build --release
:: бинарник: target\release\linesort.exe
linesort.exe -V
```

## Использование

```
linesort [ОПЦИИ] <вход...>
```

<вход> — файлы и/или каталоги. Каталог: каждый файл обрабатывается
отдельно (`имя_sorted.ext` рядом с исходным); `--merge` объединяет все
файлы каталога в один выход (тогда обязателен `-o`).

### Основные опции

| Опция | Описание |
| --- | --- |
| `-o, --output F` | выходной файл (для одного входа или `--merge`) |
| `--merge` | объединить все входы в один файл |
| `--suffix S` | суффикс выхода при per-file обработке (по умолчанию `_sorted`) |
| `--no-sort` | не сортировать: только дедуп, исходный порядок строк |
| `-u, --unique` | удалить дубликаты строк |
| `-n, --numeric` | естественная сортировка (числа как числа) |
| `-f, --ignore-case` | без учёта регистра (ASCII) |
| `--desc` | по убыванию |
| `-c, --truncate N` | обрезать строки до N символов (Unicode, не байтов) |
| `--trim` | убрать пробелы по краям строк |
| `--skip-empty` | удалить пустые строки |
| `--skip-prefix S` | удалить строки, начинающиеся с S (например `#`) |
| `-e, --encoding E` | кодировка входа: `utf8` (умолч.) \| `cp1251` \| `koi8-r` \| `ibm866`; выход всегда UTF-8 |
| `--part-lines N` | разбить выход на части по N строк |
| `--part-bytes N` | разбить выход на части по N байт (`128M`, `2G`...) |
| `-m, --memory SZ` | бюджет памяти (умолч. `512M`): `256M`, `1G`, `1500M`... |
| `-j, --jobs N` | число потоков сортировки (умолч. — все ядра) |
| `--fanin N` | серий за проход слияния (умолч. 64) |
| `--tmp-dir D` | каталог временных файлов (по умолчанию `.linesort_tmp` рядом с выходом; должен вмещать ~объём входа) |
| `-q, --quiet` | без прогресса, только итог и ошибки |
| `--verbose` | подробный журнал (серии, проходы) |
| `--overwrite` | перезаписывать существующие выходы |
| `--dry-run` | показать план и выйти |
| `-h, --help` | справка (рус.) |
| `-V, --version` | версия |

Полная справка: `linesort --help`.

### Примеры

```bash
# Алфавитная сортировка с дедупом:
linesort -u words.txt                          # -> words_sorted.txt

# Числа по возрастанию, обрезать строки до 40 символов:
linesort -n --truncate 40 data.csv -o result.csv

# Каталог: каждый файл отдельно, дедуп + по убыванию:
linesort -u --desc logs_dir/

# Весь каталог в один файл, вход в cp1251:
linesort --merge -u -e cp1251 archive/ -o all.txt

# Большой файл: 2 ГиБ памяти, 8 потоков, выход частями по 10 млн строк:
linesort -u -m 2G -j 8 --part-lines 10000000 huge.txt -o out.txt

# Только дедуп, порядок как во входе:
linesort -u --no-sort words.txt

# Прогресс пишется в stderr, поэтому данные можно писать в stdout:
linesort -u data.txt -o /dev/stdout > result.txt
```

## Как устроена внешняя сортировка (важно для больших файлов)

Память ограничена внешней сортировкой со слиянием (external merge sort):

```
вход ──чтение чанками по 8 МиБ──> арена серии (бюджет --memory)
     ──бюджет исчерпан──> параллельная сортировка долей (jobs потоков)
     ──> серия (run) во временный файл ──> ... повтор ...
все серии ──> k-сторонее слияние кучей (fanin за проход) ──> выход
```

* Дедупликация выполняется при записи: после сортировки повторы идут
  подряд и убираются сравнением с предыдущей строкой — ноль дополнительной
  памяти.
* Если серий больше `--fanin`, выполняются укрупняющие проходы (группы
  сливаются параллельно), число проходов ~ log_fanin(серий).
* `--no-sort` реализован двумя прогонами внешней сортировки по
  (строка, номер строки): группировка дубликатов с сохранением первого
  вхождения, затем восстановление исходного порядка по номеру.

### Оптимизации

* **SIMD-поиск переводов строк** (AVX2/SSE2, автоопределение; скалярный
  fallback) — до 32 байт за такт на границах строк.
* **Аренные строки**: строки серии лежат в одной большой `Vec<u8>`,
  сортируются только 8-байтовые ссылки `{offset: u32, len: u32}` — ноль
  аллокаций String, cache-friendly доступ.
* **Параллельная сортировка**: серия делится на `jobs` долей, каждая
  сортируется своим потоком (`std::thread::scope`), затем доли сливаются
  ленивой кучей при записи серии.
* **Многофайловое слияние** группами с параллельным выполнением.
* **Конвертация кодировок** cp1251/koi8-r/ibm866 → UTF-8 по статическим
  таблицам (256 значений, без зависимостей).
* **Атомарная запись**: выход пишется во временный `.part`-файл и
  переименовывается в финальное имя только после успешного завершения.

### Что считается «строкой»

* Разделитель — `\n`; `\r\n` нормализуется в `\n` (CRLF-файлы читаются
  корректно).
* Последняя строка без завершающего `\n` обрабатывается как обычная.
* Декодирование в UTF-8 происходит ДО сравнения, поэтому кириллица в
  cp1251/koi8-r/ibm866 сортируется по алфавиту, а не по байтам исходной
  кодировки.
* Байтовая сортировка UTF-8 для русского алфавита совпадает с алфавитным
  порядком (а-я); `ё` идёт после `е` — как в Unicode-коллации по умолчанию.

## Ограничения

* Регистронезависимое сравнение (`-f`) — только для ASCII-букв (как у
  GNU `sort -f`); кириллица сравнивается байтово.
* `-e/--encoding` применяется ко всем входам задачи (разные кодировки в
  одном запуске не смешиваются).
* Каталоги обходятся без рекурсии (только верхний уровень).
* Временный каталог должен вмещать примерно объём входа (серии внешней
  сортировки); по умолчанию он создаётся рядом с выходным файлом.
* Арена серии использует u32-смещения: одна серия не длиннее 4 ГиБ.
  Задавать `--memory` выше 4G смысла нет: серия всё равно закрывается
  на потолке (выводится предупреждение), а сам бюджет выше потолка в
  версиях до 1.0.1 вызывал переполнение u32 и панику.

## История версий

### 1.0.1

* **Исправлена паника на файлах больше 4 ГиБ** (`slice index starts at
  4294967264 but ends at 2`, `arena_get`): при `--memory` выше 4G арена
  серии перерастала u32-смещения `LineRef` и `off + len` переполнялся.
  Теперь вводится жёсткий потолок серии `ARENA_MAX` = 4 ГиБ − 64 КиБ:
  серия закрывается на потолке независимо от бюджета, а при `--memory`
  выше потолка выводится предупреждение. Проверено сквозным тестом
  (сборка с заниженным потолком, файл в 5 раз больше потолка серии,
  побайтовая сверка с `sort -u`).
* **Исправлен порядок строк в `--no-sort` при номерах вхождений ≥ 10**
  (баг был и в 1.0.0, всплыл на многосерийных прогонах): первый прогон
  сортировал пары «строка\x00номер» в байтовом режиме, и при равных
  строках номер сравнивался как текст («10» < «2»), из-за чего
  «первое вхождение» выбиралось неверно. Прогон переведён на
  естественную сортировку (номера — как числа), порядок входа
  восстанавливается точно; сверен с `awk '!seen[$0]++'` на 3.9 млн
  строк. Добавлен юнит-тест `test_dedup_no_sort_order`.
* Строка длиннее 4 ГиБ теперь даёт чистую ошибку (exit 2) вместо
  порчи данных; юнит-тест потолка `test_arena_cap_capped_to_arena_max`.
* Юнит-тестов теперь 20 (было 18), функциональные — 38, все зелёные.

## Результаты замеров (эталонные прогоны)

Тестовая машина: 2 ядра, 4 ГБ RAM. Генератор: scripts/gen_bigfile.py
(40% дубликатов, слова/числа/CSV-строки, кириллица + латиница).

### Прогон 1: файл 1.57 ГБ, 125 732 694 строк, бюджет 128M

| Утилита | Время | Пиковый RSS | Серий |
| --- | --- | --- | --- |
| linesort (`-u -m 128M -j 2`) | 86 c | 355 МБ | 12 |
| GNU sort (`sort -u -S 512M`) | 77 c | 515 МБ | — |

### Прогон 2 (многопроходность): тот же файл, бюджет 16M, fanin 32

linesort: 93 серии, 1 укрупняющий проход, 75 c, результат идентичен.

### Прогон 3: файл 428 МиБ, 33.5 млн строк, бюджет 64M, fanin 128

linesort: 20.5 c, пиковый RSS 144 МБ, 7 серий.

Во всех прогонах результат linesort байт-в-байт идентичен `sort -u`.

## Структура исходника (один файл `linesort.rs`)

Исходник собран из модулей (в порядке следования):

| Секция | Назначение |
| --- | --- |
| `misc` | форматирование чисел/размеров, тип ошибок, `parse_size` |
| `progress` | прогресс-бар, фазы, ETA, итоговый отчёт |
| `encoding` | таблицы cp1251/koi8-r/ibm866 и декодер в UTF-8 |
| `simd` | быстрый поиск `\n` (AVX2/SSE2/скаляр) |
| `io` | построчный читатель, MultiReader, PartWriter с разбивкой |
| `arena` | арена строк + 8-байтовые ссылки LineRef |
| `cmp` | компараторы: байтовый, естественный, регистронезависимый |
| `chunksort` | параллельная сортировка долей + heap-слияние |
| `extsort` | внешняя сортировка: серии, k-way merge, укрупнение |
| `app` | конвейер задачи: фильтры строк, `--no-sort`, отчёты |
| `cli` | разбор аргументов, справка |
| `main` | входная точка, обход каталогов, план, сводка + тесты |

## Выходные коды

* `0` — успех;
* `1` — ошибка аргументов (справка по `--help`);
* `2` — ошибка ввода-вывода или данных.

Прогресс и журнал пишутся в **stderr**, поэтому stdout свободен для
данных (`-o /dev/stdout` или конвейеры).
